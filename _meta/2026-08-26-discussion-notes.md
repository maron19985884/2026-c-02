> **記録日時**: 2026-08-27 10:28

> **参加者**: 中村さん（ワークショップメンバー）、Bob (IBM Bob Agent)

---

## 1. 近藤さんの指摘：「spec.md 以外の準拠文書があると AI が誤った方に倒れるリスク」

### 指摘の内容

Spec Kit の設計思想は「`spec.md` が唯一の真実」。`plan.md` も `tasks.md` もすべて `spec.md` から派生する。この雛形では `/speckit.design` による設計書（`basic-design.md` 等）を `spec.md` の下流として位置づけているが、設計書が存在する状態で `/speckit.implement` を走らせると、AI は `tasks.md`（`spec.md` 由来）と `detailed-design.md` の両方を参照し、矛盾があればどちらかに引っ張られる。

### Bob の見解

指摘は正しい。ただし `speckit.implement.md` のコマンドは `tasks.md` と `plan.md` を必須入力として読むが、`basic-design.md` / `detailed-design.md` を読む指示はない。つまり**設計書は AI の実装には直接影響しない**構造になっている。

これは意図的な設計（設計書はウォーターフォールの承認証跡であり、AI の動作制御は `spec.md` → `plan.md` → `tasks.md` の系列のみが担う）と解釈できるが、**人間が承認した設計書の内容と AI が実装するコードが食い違う**という事態は起きえる。

### 対策の方向性（会議で出た案）

- 人間用の設計書は別リポジトリで管理する
- ウォーターフォールの一連の流れを流し切った後に設計書を生成する（ズレが出ない）
- ただし「実装後に設計書を作る」はウォーターフォールの承認プロセスとしては本末転倒になるトレードオフがある

## 2. ウォーターフォールと Spec Kit の哲学的矛盾

### 根本的な対立

| Spec Kit の前提 | ウォーターフォールの前提 |
|---|---|
| `spec.md` は Living Document（常に更新され続ける） | フェーズで確定した文書は原則変更しない |
| 変更はフローの中で自然に吸収する | 変更は承認ゲートを通じて管理する |

この2つは**哲学レベルで矛盾**している。

### 具体的にどこが壊れるか

**ケース1：設計フェーズ中に仕様の矛盾が発覚した場合**

- Spec Kit の本来の動き：`/speckit.clarify` で `spec.md` を更新する
- ウォーターフォールの制約：フェーズ確定後は `/speckit.change` による変更要求書が必要
- 結果：変更要求書を1枚起票するたびに `spec.md` が更新される。承認記録と実物の `spec.md` の乖離が蓄積していく

**ケース2：実務的な仕様変更の連鎖**

`spec.md` を直すと `plan.md` の Constitution Check が再び必要になり、`tasks.md` も作り直し、承認記録も再起票——変更のたびにフェーズ遡及の手続きコストが発生する。

### 「仕様をさかのぼって改変しない」前提なら機能するか

理論上は機能するが、条件が厳しすぎる。

- 要件定義書が完全かつ曖昧さゼロで書かれている
- 顧客・ステークホルダーが要件を確定後に変えない
- 技術的制約が設計前にすべて判明している

実務ではこの3条件が同時に成立することはほぼない。特に金融機関のように規制変更・顧客要望が後出しで来る環境では、ほぼ机上の空論。

### 現実的なスコープ分割（佐藤さんの想定）

> 要件定義・基本設計は人間が実施（金融機関のためユーザーとの調整が必須）し、詳細設計〜製造〜単体テストを Spec Kit で代替、結合テスト以降は人間が戻る流れ

このスコープ分割は現実的。ただしこの場合も、渡された要件定義書の完成度が低ければ結局 `spec.md` 以降でズレが生じるため、**要件定義書の品質担保が雛形の外側の重要な前提条件**になる。

## 3. Spec Kit に備わっている齟齬防止の仕組み

### 備わっている仕組み（3層）

**層1：生成前の曖昧さ低減 — `/speckit.clarify`**

`spec.md` 生成後に8カテゴリを走査して最大5問の質問を人間に投げ、回答を `spec.md` に書き戻す。ただし上限が5問のため、複雑な要件では不十分。残った曖昧さは AI の「informed guess（根拠ある推測）」で埋められる。

**層2：受け入れシナリオの強制 — `spec-template.md`**

各ユーザーストーリーに必ず Given/When/Then 形式の受け入れシナリオを書かせる。「テストできない要件は書けない」という制約として機能し、曖昧な要件の混入を構造的に抑制する。ただし `spec.md` 内部の自己整合性を高める仕組みであり、「`spec.md` が `requirements.md` の意図を正しく反映しているか」は検査しない。

**層3：下流の整合性チェック — `/speckit.analyze`**

`spec.md`・`plan.md`・`tasks.md` の3ファイル間の矛盾・漏れ・重複を検出。ただし読み取り専用で修正はしない。

### 備わっていない仕組み（本質的な弱点）

| 必要な仕組み | 現状 |
|---|---|
| `requirements.md` → `spec.md` の忠実性検証 | **ない** |
| 人間の意図と AI の解釈のズレの検出 | **ない** |
| 仕様変更の影響範囲の自動追跡 | **ない** |
| 設計書と実装コードの整合検証 | **ない** |

**最大の空白は「`requirements.md` → `spec.md` の翻訳が正しいかを検証する仕組みがない」点。**

現状の回避策は「人間が `spec.md` をレビューして取り違えを発見する」という人間の読解力への依存だけ。

### 結論

> 「低減する仕組み」はありますが、「防止する仕組み」はありません。

これは Spec Kit 固有の問題ではなく、**「自然言語の要求を形式的な仕様に変換する」という行為に本質的に伴う不確かさ**。人間がウォーターフォールのレビュープロセスで何十年もかけて対処してきた問題を、AI が自動解決できるという前提自体が過剰な期待。

## 4. アジャイルでも同じ問題か

同じ問題が発生する。ただしアジャイルでは緩和される条件が2つある。

**緩和条件1：フィードバックループが短い**

スプリント単位で動くものを顧客に見せるため、「`spec.md` の解釈ミスによる実装のズレ」がスプリント内で発覚する。ウォーターフォールでは数ヶ月後のテストフェーズまで発覚しない。

**緩和条件2：`spec.md` が更新されることを前提とした設計**

Spec Kit 公式が `spec.md` を "Living Document" と位置づけているのは、アジャイルのスプリントごとに更新されることを想定しているため。ウォーターフォールで「確定後は変更しない」運用をすると、この前提が崩れる。

ただし緩和されるだけで解消はされない。アジャイルでも「要求文書の意図と `spec.md` の乖離」は毎スプリント起き得るため、`/speckit.clarify` の5問制限と人間レビューへの依存という構造的弱点は残る。

## 5. 「AI駆動開発で人間の負荷が上がる」の構造

### 負荷の移行

従来（書く負荷）：
```
要件定義 → 設計書執筆 → コーディング → テスト仕様作成
```

AI 駆動開発（レビュー負荷）：
```
要件定義 → (AI) → spec.md → (AI) → plan.md → (AI) → コード
         ↑                  ↑                  ↑
       レビュー            レビュー            レビュー
```

「書いた人間は自分の意図を知っているが、レビューする人間は AI が何を考えて書いたかを読み解く必要がある」という非対称性が生じる。

### 負荷の性質の変化

| 従来の負荷 | AI 駆動開発後の負荷 |
|---|---|
| 繰り返し作業（テンプレート転記・フォーマット合わせ） | 判断負荷（AI の解釈が正しいかを確認する） |
| 記憶負荷（前フェーズと整合させながら書く） | 発見負荷（AI が何を省略・仮定したかを見つける） |
| 属人的なばらつき（担当者のスキルで品質が変わる） | 責任負荷（AI の生成物に署名する重み） |

繰り返し・記憶・ばらつきは減るが、**判断・発見・責任という高度な認知負荷が残り、むしろ集中的に要求される**。

### Spec Kit 固有の問題

レビューすべき成果物が多すぎる（`spec.md`・`plan.md`・設計書3種・`tasks.md`・コード・`test-plan.md`・フェーズ承認記録×6）。すべてに同じ重みでレビューを求める設計は、**レビューの形骸化**を招くリスクがある。

## 6. ばらつきの2層構造（本質的な整理）

```
【表層のばらつき】← Spec Kit / プロンプトで低減できる
  - 成果物のフォーマット・構成
  - フェーズの進め方・順序
  - ドキュメントの存在有無
  - Lint 違反・コーディングスタイル

【深層のばらつき】← 自動では吸収できない
  - 要件の解釈の違い
  - 仕様の曖昧さへの対処方針
  - ビジネスロジックの優先順位の取り違え
  - 「書かれていないこと」をどう補うか
```

**Spec Kit が解決しているのは表層のみ。**「形のばらつき」は減らせるが「意味のばらつき」は減らせない。

### なぜ深層のばらつきは自動で吸収できないか

根本的な理由は、**「正解が人間の頭の中にしかない」**から。要件定義書に書かれていないことを AI が何らかの仮定で埋める際、その仮定が「その組織の常識」と一致するかは、書いた人間が読んで確認するまでわからない。

この問題は AI 以前から存在していた。人間が仕様書を書いていた時代も、「書いた人間の意図」と「読んだ実装者の解釈」のギャップは常にあった。AI はこのギャップを「なくす」のではなく、「可視化する速度を上げる」だけ。

## 7. ワークショップの成果への再評価

### Spec Kit の実際の貢献範囲

| 項目 | Spec Kit の効果 |
|---|---|
| 担当者が変わっても同じフローを辿る | ✅ 高い効果 |
| 成果物の構造・フォーマットが揃う | ✅ 高い効果 |
| レビュー観点が属人化しない | ✅ 中程度の効果 |
| 要件の解釈ミスを防ぐ | ❌ ほぼ効果なし |
| 仕様の曖昧さを自動解消する | ❌ 効果なし（低減のみ） |

### 意味のある貢献として残るもの

1. **形のばらつきを減らすことで、人間のレビューを本質的な判断に集中させられる**  
   担当者が毎回フォーマットを考える作業がなくなれば、限られたレビュー時間を「解釈の確認」に使える

2. **解釈のばらつきが発生する箇所を早期に浮かび上がらせる**  
   `/speckit.clarify`・`/speckit.analyze` は「ここに曖昧さがある」という箇所を実装前に可視化する。発覚が遅れるほどコストが上がるため、早期発見の価値は実際にある

3. **変更管理の記録を自動化する**  
   `/speckit.change` による変更要求書の自動生成は、「誰がいつどんな変更を承認したか」の証跡を標準化する。解釈のばらつきとは別の、監査・説明責任のばらつき低減として機能する

## 8. 来週の認識合わせに向けた示唆

### 先に人間が決めるべきこと（技術修正より優先）

1. **雛形が担うスコープの境界線**（詳細設計〜単体テストか、それ以前も含むか）を `docs/overview.md` に一文で書く
2. **設計書（`/speckit.design` 生成物）と `spec.md` が矛盾した場合のルール**を `constitution.md` に明記する
3. **SAST の組み込み位置**を `quality-gate.yml` のコメントと `docs/guides/waterfall-preset-guide.md` に追記する

これらは技術修正ではなく**方針の明文化**であり、人間（チーム）が決めてから AI に書かせる順序が適切。

### 発表に向けた推奨メッセージ

> 「Spec Kit の導入で、開発プロセスの形式的なばらつき（フォーマット・フロー・承認記録）は大幅に低減できる。一方、要件解釈の深層的なばらつきは自動では吸収できず、人間のレビューが引き続き必要である。この雛形はそのレビューを効率化・標準化するためのものである。」

### レビューの深度グラデーション（形骸化防止）

全成果物に同じ重みでレビューを求めるのは非現実的。以下のようなグラデーションの設計が実用的：

| 成果物 | 推奨するレビュー深度 |
|---|---|
| `requirements.md` | 必ず人間が書く・深くレビュー |
| `spec.md` | AI生成だが `requirements.md` との対応を必ず確認 |
| `plan.md` / 設計書 | テックリードが構造のみ確認、細部は省略可 |
| `tasks.md` | PMが工数感のみ確認 |
| `test-plan.md` | テスト担当が受け入れ基準の網羅性のみ確認 |
| ソースコード | Lint 通過 + 差分レビュー |

## 9. 大野さんの整理への補足

> 「そもそも標準化・ばらつき抑制という導入目的に立ち返って評価すべき」

この視点が最も重要。**「AI に任せれば品質が上がる」ではなく「AI を使って人間が品質を保つコストを下げる」**という目的の再定義が、過剰な期待を防ぎ、実務で使える道具として定着させる鍵になる。
