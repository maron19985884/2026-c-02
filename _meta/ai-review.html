詳細所見 — 優先度順

CRITICAL（リリース前に必須対処）

CRITICAL constitution.md に未解決プレースホルダーと ※要修正 が残存
.specify/memory/constitution.md

「[組織名]」「[例: 80%]」「[標準的なCSSルール]」「[WCAG 2.1 AA]（角括弧のままで定義として機能しない）」「※要修正」が複数残っている。憲法は最優先ルールとして CLAUDE.md から @ インポートされるため、AIがこれらを実際の制約として解釈してしまうリスクがある。特に「[標準的なCSSルール]」は意味不明な指示になる。

→ 対処: プレースホルダーを実値または「未定義（プロジェクトで記入）」という明示的な表現に置き換える。WCAG 2.1 AA は角括弧を外して正式に記述する。

CRITICAL plan-template.md のソースコード構造が Next.js+Express 固定
.specify/templates/plan-template.md

backend/src/models/、frontend/src/components/ という具体的なディレクトリツリーがハードコードされ、「Structure Decision: Web application (Next.js frontend + Express.js backend)」と書かれている。Python CLI や Java バックエンドのプロジェクトに適用すると、AIがこの構造を前提に計画を生成してしまう。

→ 対処: 「Option 1: Single project」「Option 2: Web application」「Option 3: Mobile+API」のような選択肢形式に戻し、具体技術名を除去する。

CRITICAL speckit.plan.md の「技術を選ばない」宣言と plan-template.md の決め打ちが矛盾
.claude/commands/speckit.plan.md & .specify/templates/plan-template.md

コマンドファイルは「Do NOT select technology」と明示しているのに、参照先のテンプレートには Next.js / Express.js 固定の構造が書かれている。AIは template をコピーして埋めるため、コマンドの制約より template の内容が優先されてしまう。命令と素材が矛盾する構造は AI の挙動を不安定にする。

→ 対処: template 側を技術非依存の形式に修正し、コマンドとテンプレートの一貫性を確保する。

HIGH（ウォーターフォール運用に影響）

HIGH テストフェーズの成果物テンプレートが存在しない
docs/ 全体

waterfall-preset-guide.md の対応表にはテストフェーズがあるが、「テスト計画書」「テスト報告書」「テスト結果承認記録」に対応するテンプレートが一切ない。ウォーターフォールの最大の価値は各フェーズの成果物が揃っていることにあるため、この欠如はフロー全体の信頼性を下げる。

→ 対処: docs/test-plan-template.md（テスト計画）、docs/review-gate-template.md（フェーズ承認記録）を新規作成する。

HIGH 各フェーズの完了定義（DoD）が未定義
docs/waterfall-preset-guide.md

「要件定義フェーズの完了」とはいつか？ spec.md が生成されたとき？ 顧客が承認したとき？ 承認ゲートの存在は言及されているが、「何をもって完了とするか」の判定基準が書かれていないため、誰が見ても同じ判断を下せない。

→ 対処: 各フェーズに DoD（Definition of Done）チェックリストを追加する。 /speckit.checklist コマンドの活用先としても自然な拡張になる。

HIGH 変更管理プロセスが言及のみで実体がない
docs/waterfall-preset-guide.md

「計画確定後の要件変更は変更管理プロセス（別途、変更要求書）を経由させる」と書かれているが、その「変更要求書」テンプレートが存在しない。ウォーターフォールで最も頻繁に問題になるのが要件変更の管理であるため、実体のないプロセス参照はリスクになる。

→ 対処: docs/change-request-template.md（変更要求書）を作成する。

MEDIUM（汎用性・保守性に影響）

MEDIUM CLAUDE.md の命名規則・スコープ外リストが書籍アプリ固有
CLAUDE.md

「BookCard.tsx」「cartUtils.ts」「CartItem」「Order」という具体例、および「ログイン・会員管理」「決済処理」などのスコープ外リストが書籍販売アプリのもの。汎用テンプレートとして配布すると、新規プロジェクトの AI が誤ってこれらの制約を適用してしまう可能性がある。

→ 対処: 命名規則の例を汎用的な記号（例: FeatureName.tsx）に置き換え、スコープ外リストを「プロジェクトで記入」形式にする。

MEDIUM speckit.implement.md の .gitignore 検証が Node.js 固定
.claude/commands/speckit.implement.md

「.gitignore に Node.js/TypeScript と Docker のパターンが含まれているか検証する」という命令がある。これは現プロジェクトには適切だが、汎用テンプレートとして Python や Java プロジェクトに使うと不適切な検証が走る。

→ 対処: 「plan.md の技術スタックを参照し、その言語に対応するパターンを確認する」という動的な命令に書き換える。

MEDIUM requirements-template.md に版管理・承認欄がない
docs/requirements-template.md

ウォーターフォールでは要件定義書は正式ドキュメントとして版管理・承認が必要。現テンプレートには変更履歴テーブルも承認欄もなく、誰が・いつ・何を変更したかの追跡ができない。requirements.md 本体には変更履歴があるのに、テンプレートにはない点も矛盾している。

→ 対処: 変更履歴テーブルとフェーズゲート承認欄（承認者・承認日・承認条件）を追加する。

MEDIUM spec-template.md が英語、他ドキュメントが日本語で言語不統一
.specify/templates/spec-template.md 他

spec-template.md、plan-template.md、tasks-template.md は英語。requirements-template.md、constitution.md、CLAUDE.md は日本語。AI が生成する成果物の言語が揺れると、レビューや検索効率が下がる。また日本語環境の開発者にとってテンプレートが英語だと記入障壁になる。

→ 対処: テンプレート言語をプロジェクトで統一する方針を constitution.md または docs/overview.md に明記する。

LOW（品質向上）

LOW constitution.md セクション7「設計ルール」の書式が不揃い
.specify/memory/constitution.md

セクション1〜6はスペース区切りの箇条書きだが、セクション7は-基本設計書について（ハイフンの後にスペースなし）と書式が崩れている。AIの解析精度に軽微な影響がある可能性がある。

→ 対処: 他セクションと同様のフォーマットに統一する。

LOW speckit.checklist.md コマンドが docs/ のガイドを参照していない
.claude/commands/speckit.checklist.md

waterfall-preset-guide.md や requirements-template.md がフェーズゲートの基準として存在しているのに、チェックリスト生成コマンドからそれらへの参照がない。チェックリストがプロジェクト固有の基準を反映しにくい構造になっている。

→ 対処: 「docs/waterfall-preset-guide.md の DoD を参照してフェーズゲートチェックリストを生成できる」旨を明記する。
