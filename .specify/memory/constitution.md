# プロジェクト憲法（Constitution）

> Spec Kit公式の位置づけ: `/speckit.constitution` により生成・更新される、
> コード品質・テスト基準・UX一貫性・パフォーマンス要件・技術的意思決定ルールなど
> チームの長期的な原則を記録するファイル。単一機能の要件ではなく、
> チーム全体の合意事項を書く場所として公式に位置づけられています。
> 出典: https://knightli.com/en/2026/05/25/github-spec-kit-spec-driven-development/
>
> **本プロジェクトでの位置づけ**: `user_requirements.md`（個人運営オンライン書店・購買フロー特化版）の
> 要件をもとに確定させた版。以後はプロジェクトを通してそのまま参照し、変更が必要な場合は
> 本ファイルの改訂手続き（レビュー＋承認）を経て更新する。プロジェクト個別の微調整が必要な場合は
> `.specify/templates/overrides/` またはpresetで上書きする。

## 1. コード品質原則（Code Quality）
- 本プロジェクトのコードは、静的解析（Lint）で **エラー0件** を必須とする。警告（Warning）は許容するが放置せず、都度Issue化して解消する。
- Lintツールは技術選定書（`docs/tech-stack-template.md`）で確定した言語・スタックに従う（例: JavaScript/TypeScript → ESLint、Python → Ruff）。具体的なルールセットは本ファイルに直接書かず、`docs/lint-preset-guide.md` の手順でpreset化し、`.specify/templates/overrides/` または独自presetパッケージとして管理する。
- Lint基準の変更は本憲法の改訂手続き（レビュー＋承認）を経て反映する。

## 2. テスト基準（Testing Standards）
- 主要なビジネスロジック――特にカートの数量変更・小計/合計金額のリアルタイム再計算（U-08, U-09, U-10）、注文フォームの必須項目・形式チェック（U-12, U-13）――には単体テストを必須とし、カバレッジ目標は **80%以上** とする。
- 「商品一覧 → 商品詳細 → カート → 注文フォーム → 注文完了」の主要購買フロー（要件定義書 4章 画面遷移サマリー）は、最低1本のハッピーパスをE2Eテストで担保する。それ以外の結合テストの要否は機能の重要度に応じて判断する。
- テストのない実装はレビューで差し戻す。

## 3. UX一貫性（UX Consistency）
- UIは技術選定書で確定したCSS／デザインルールに準拠する。
- 商品一覧・商品詳細・カート・注文フォーム・注文完了の全5画面で、ヘッダー／ナビゲーション、エラーメッセージの表示形式、空状態（例: カートに商品が0件の場合）の扱いを統一する。
- アクセシビリティは **WCAG 2.1 AA** を目標とする。

## 4. パフォーマンス要件（Performance）
- 個人運営規模のオンライン書店であることを前提に、主要画面・APIのレスポンスは **95パーセンタイルで1秒以内** とする。
- 想定同時接続数：**50**（個人運営規模の前提。将来トラフィックが増える場合は本項を見直す）。
- スケーラビリティ方針：初期は単一サーバーでの垂直スケールを許容し、決済・在庫管理等の将来拡張（現状スコープ外）に着手する段階で水平スケールを再検討する。

## 5. 技術的意思決定ルール（Technical Decision Rules）
- 使用技術・アーキテクチャは `/speckit.plan` の前に **技術選定書（`docs/tech-stack-template.md`）** で人間が確定させる。`plan` フェーズで技術を選び直さない。
- 現時点で `docs/tech-stack-template.md` は未記入のため、`/speckit.plan` 実行前に必ず記入・確定する。
- 新規依存ライブラリを技術選定書に追加する際は、選定理由を明記する。
- ログイン・会員管理／決済処理／在庫管理／管理画面／レビュー・評価／検索・フィルターは要件定義書（`user_requirements.md` 3章）で明示的にスコープ外とされているため、これらを実現する技術・外部サービスは本フェーズでは選定しない。

## 6. 開発方法論の運用ルール
- 本プロジェクトは新規開発（グリーンフィールド）であり、改修対象となる既存システムは存在しない。よってBrownfield運用（`docs/brownfield-guide.md`）は非該当とする。
- 開発はSpec Kit標準フロー（`/speckit.specify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`）に従い、フェーズごとの正式な承認ゲート（ウォーターフォール運用）は設けない。要件定義書（`user_requirements.md`）・技術選定書・本憲法の3点を土台に、Spec Kitのフローをそのまま進める。
- 将来、複数人体制やフェーズ承認が必要になった場合は `docs/waterfall-preset-guide.md` に従ってpresetを追加する。

## 7. 設計ルール
- 基本設計書について、HTMLベースでUMLに準拠して作成する。
- 詳細設計書について、HTMLベースでパラメータ、修正対象ファイル、処理概要、In/Out詳細をまとめて作成する。
- テーブル定義書について、HTMLベースで作成する。対象は書籍・カート・注文（および注文明細）のテーブルとする。

## 8. スコープガードレール（本プロジェクト固有）
- 要件定義書（`user_requirements.md` 3章）でスコープ外と明示された以下の機能は、本憲法の改訂手続きを経ない限り実装しない：ログイン・会員管理、決済処理、在庫管理、管理画面、レビュー・評価、検索・フィルター。
- 対象画面は次の5つに限定する：商品一覧／商品詳細／カート／注文フォーム／注文完了（要件定義書 2章）。
- スコープ外機能の実装が必要になった場合は、`user_requirements.md` の改訂と本憲法の改訂手続きの両方を経てから着手する。
