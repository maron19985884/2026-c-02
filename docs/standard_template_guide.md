# 生成 AI 開発 標準テンプレート 利用ガイド

Claude Code（生成 AI）を使ったチーム開発で、担当者・セッションごとの成果物のばらつきを防ぐための標準テンプレートである。
背景となった分析は `docs/prompt_analysis.md`（プロンプト手法比較分析レポート）を参照。

## 基本原則

**Claude はセッションをまたいだ一貫性を持たない。決めていないことは必ずばらつく。**

したがって標準化は「Claude が読むファイルに、決定事項を書く」ことでのみ実現できる。
本テンプレートは、情報を役割ごとに次の層に振り分ける。

| 層 | ファイル | 入れるもの | 効き方 |
|---|---|---|---|
| ① 常時規約 | `CLAUDE.md` | 決定事項・規約・禁止事項 | 全セッションに自動適用 |
| ② 決定の記録 | `docs/decisions.md` | 仕様の空白を埋めた経緯 | CLAUDE.md の裏付け・監査証跡 |
| ③ 機械的強制 | lint / CI / `.claude/settings.json` | 検証可能なルール | AI の解釈に依存せず 100% 効く |
| ④ 工程手順 | プロンプト or スキル | フェーズごとの定型指示 | 呼んだときだけ適用 |

## 各ファイルの書き方

### CLAUDE.md（層①）

- **コードから読み取れることは書かない**（ディレクトリ構成の説明などは不要。Claude は自分で読める）
- **「決めないとばらつくこと」だけを書く**: ポート番号・API レスポンス形式・URL 設計・DB 命名規則・禁止事項
- 「〜が望ましい」ではなく**宣言形**で書く（例: 「レスポンスは常に `{ data, error, message }`」）
- 目安は 100〜150 行以内。超えたら `docs/` に切り出してリンクする

### docs/decisions.md（層②）

- 要件定義書の空白（今回の例: 注文番号フォーマット・URL 設計）を発見するたびに 1 行追記する
- 追記したら CLAUDE.md の「決定事項」セクションにも反映する（Claude が実際に読むのは CLAUDE.md 側）

### 機械的強制（層③）

- 「`console.log` 禁止」「`any` 禁止」のような検証可能なルールは、CLAUDE.md に書くだけでなく ESLint ルール + CI で落とすのが確実
- 原則: **機械で検証できるルールは機械に、判断が要るルールだけを CLAUDE.md に**
- `.claude/settings.json` にはチーム共通の権限設定を置く（個人設定は `settings.local.json`）

### 工程手順（層④）

- 設計 → 実装 → テストの工程順序と、テストの粒度（ユニット / 結合の分離など）はプロンプトで明示する
- 推奨パターン（設計フェーズ先行型）:

```text
1. CLAUDE.md を確認し、規約に違反していないか検証しながら外部設計書を作成してください
2. 外部設計書をもとに内部設計書・DB 設計を作成してください
3. 設計書に基づいてバックエンドを実装してください
4. フロントエンドを実装してください
5. ユニットテスト（ロジック単体）と結合テスト（API エンドポイント）を分けて実装してください
```

- 各フェーズの冒頭に「CLAUDE.md を確認し」を入れると、設計書生成時にも規約が引き継がれる
- 定型化が進んだら `.claude/skills/` のスラッシュコマンドに昇格させる（コピペ運用の個人差をなくす）

## 新しいプロジェクトへの展開手順

1. main ブランチに本テンプレート一式（`CLAUDE.md`, `docs/decisions.md`, `.claude/settings.json`）を置く
2. `CLAUDE.md` のプロジェクト概要・技術スタック・コマンド・決定事項をそのプロジェクトの値に書き換える
3. 全担当者が feature ブランチを切る**前に** 1〜2 を完了させる（ブランチを切った時点で CLAUDE.md が存在する状態にする）
4. 開発中に見つかった仕様の空白は `docs/decisions.md` → `CLAUDE.md` の順で埋めていく
