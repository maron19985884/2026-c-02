## 結論
基本設計書・詳細設計書・テーブル定義書は、`docs/design-templates/` にあるHTMLテンプレートをコピーして作成する。各テンプレートには必須セクションの見出しと、ライト/ダーク両対応のスタイルシートがあらかじめ組み込まれている。空欄・プレースホルダー（`[記入: ...]`）を埋めるだけで、憲法セクション7の要件を満たせる。

## 背景（なぜこのガイドがあるか）
`002-book-catalog-detail` の作成時、憲法セクション7が当初「HTMLベースでUMLに準拠して作成する」としか定めておらず、実際に何を書けばよいかが曖昧だった。結果として、最初に作った基本設計書にはアーキテクチャ構成図・画面遷移図・シーケンス図しかなく、画面レイアウト・項目定義・エラー処理方針・API一覧が抜けていた。詳細設計書も同様に、処理フロー図・例外処理・呼び出し関係図が後から追加された。

このガイドと`docs/design-templates/`は、次回以降のfeature（例: 注文フォーム・注文完了画面）で同じ手戻りが起きないようにするために作成した。

## 各ドキュメントの必須セクションと、その目的

### 基本設計書（`basic-design-template.html`）

| # | セクション | 目的・入れる理由 |
|---|---|---|
| 1 | システム概要 | 本機能が何をするものかを一段落で説明する |
| 2 | アーキテクチャ構成図 | frontend/backend/DBの配置と通信経路をUML（コンポーネント図）で示す |
| 3 | 外部インターフェース仕様（API一覧） | frontendが呼び出すAPIの一覧を、契約書（`contracts/*.md`）より高いレベルで俯瞰できるようにする |
| 4 | 画面一覧 | 対象画面と対応要件（REQ/FR）の対応表 |
| 5 | 画面レイアウト・項目定義 | ワイヤーフレーム図＋各項目がどのデータ・どの要件に対応するかの一覧表。**「見た目が分かりづらい」問題に直結する最重要セクション** |
| 6 | 画面遷移図 | 画面間の遷移条件をUML（状態遷移的な図）で示す |
| 7 | シーケンス図 | 主要User Story単位で、利用者操作からDBまでの処理の流れをUMLで示す |
| 8 | エラー処理方針（共通） | 空状態・見つかりません・予期しないエラー等を横断的に統一するための状態分類表と方針。憲法セクション3（UX一貫性）への対応 |
| 9 | 非機能要件との対応 | 憲法セクション3・4等、非機能要件をどう満たすかの一覧 |

### 詳細設計書（`detail-design-template.html`）

| 項目 | 目的・入れる理由 |
|---|---|
| 呼び出し関係図（文書冒頭・1枚のみ） | モジュール間の呼び出し関係（コールツリー）を俯瞰する。実線＝関数呼び出し、破線＝HTTP通信等ランタイム境界をまたぐもの、で区別する |
| 処理概要（モジュールごと） | そのファイルが何をするかを一段落で説明する |
| 処理フロー図（モジュールごと、分岐がある場合） | 条件分岐・エラー分岐をフローチャートで示す。単純な処理（分岐のないgetter等）では省略してよい |
| 例外処理（モジュールごと） | そのモジュールで発生しうる例外・エラーケースと、検知方法・対応（ステータスコード/表示/ログ）の一覧。基本設計書の「エラー処理方針」との整合を取ること |
| パラメータ・修正対象ファイル・In/Out詳細（モジュールごと） | 関数のシグネチャ・入出力の型を一覧化する |

### テーブル定義書（`table-definition-template.html`）

| セクション | 目的・入れる理由 |
|---|---|
| テーブル一覧 | 対象テーブルとその概要 |
| カラム定義 | 物理名・論理名・型・NULL可否・デフォルト・PK/FK・説明 |
| インデックス定義 | 想定クエリに対する推奨インデックス |
| 制約 | CHECK制約等のアプリケーション/DB側の制約 |
| ER図 | テーブル間（複数テーブルの場合）の関連 |

## 使い方

1. `docs/design-templates/` から対象ファイルをコピーし、`specs/[###-feature-name]/design/` 配下に配置する
2. `[記入: ...]` のプレースホルダーを、`spec.md`・`plan.md`・`data-model.md`・`contracts/*.md` の内容を基に埋める
3. 図（SVG）は各テンプレートの `diagram-box` クラスの使用例（コメントで残してある）を参考に作成する
4. 完成したら、正本（Source of Truth）はMarkdown成果物（`plan.md`等）である旨の注記を末尾に残す（テンプレートに記載済み）

## 💡 補足
- **正本の扱い**: HTML設計書はMarkdown成果物（`spec.md`/`plan.md`/`data-model.md`/`contracts/`）を可視化したものであり、内容が食い違った場合はMarkdown側を正とする。これはSpec Kit標準のコマンド（`/speckit.plan`等）がMarkdown側しか更新しないため。HTML側の追従はfeature作業者が手動で行う必要がある。
- **Spec Kitの自動化対象外であること**: `docs/ai-review.md`（前回までの分析）で確認した通り、これらのHTML設計書はどの`.specify/scripts/`や`.claude/commands/`からも自動生成・自動参照されない。テンプレートをコピーする作業自体も手動で行うこと。
