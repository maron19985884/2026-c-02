- 憲法本文に変更理由をHTMLコメントとして埋め込むスタイルは、他セクションには例がない。
  変更履歴を憲法本体に残す方式を今後も採用するか、`docs/changelog.md`（既存の変更ログ）に

## 3. コミットにまだ反映していない気づき・改善点（要議論）

ローカル開発中に発見したが、テンプレート／憲法側の恒久ルールとしてはまだ落とし込んでいない事項。

### 3-1. 「フロント側の制約」を根拠にバックエンド検証を省略しない

- **経緯**: 004-order-checkout の `/speckit.analyze` 実行後、`data-model.md` が
  「`order_items.quantity` のバックエンド検証は、003 spec.md FR-009 のカート側制約
  （数量は1未満にならない）を踏襲し省略する」としていたが、`POST /api/orders` は
  無認証で直接呼び出し可能な公開APIであるため、`curl` で `quantity: -3` を送ると
  そのまま `totalAmount: -8400` としてMySQLに保存されてしまう不具合を確認した
  （commit `a63bf85` で修正済み）。
- **一般化した論点**: 本プロジェクトはログイン・認証がスコープ外のため、
  `backend/src/routes/` 配下の全エンドポイントが無認証で直接叩ける。
  「フロントがすでに保証しているから」を理由にバックエンド側の検証を
  spec/data-model.md 上で省略する判断は、無認証プロジェクトでは特に危険。
- **打ち合わせ論点**: この観点を
  - 憲法（`.specify/memory/constitution.md`）のテスト基準 or 新設セクションに入れるか
  - `docs/design-doc-guide.md`（詳細設計書の書き方）のレビュー観点に入れるか
  - `/speckit.analyze` 実行時のチェック項目として明文化するか
  のどこに置くのが「組織で一度だけ確定→使い回す」というひな形の運用方針
  （憲法冒頭の運用方針参照）に合うか要検討。

### 3-2. 憲法（constitution.md）のチーム内合意プロセス

- **経緯**: このプロジェクトでは、各メンバーが個別に `constitution.md` の草案を作り、
  ミーティングで持ち寄って1つに収束させる運用を取っている（初回は2026-08-05実施）。
- **打ち合わせ論点**: 今回の002〜004開発を通じて `.specify/` 側は無変更だったため、
  「憲法は一度確定すれば触らない」という運用が少なくともこの規模の機能追加では
  機能した、と言える。次にひな形を横展開する際、この「個別ドラフト→すり合わせ」
  プロセス自体をひな形の手順書（例: `docs/waterfall-preset-guide.md` や
  README 相当）に明文化するかどうかは検討の余地がある。

## 4. メタ観点：ひな形の「記入待ち」項目の扱いについて

今回の変更は大きく2種類に分けられる。

1. **テンプレートのプレースホルダー欄を実装しながら埋める／事後的に文書化する**
   （`CLAUDE.md` の命名規則・スコープ外機能、`docs/tech-stack-template.md` の
   デザイントークン・E2Eツール）
2. **ひな形の恒久ルール（憲法）自体の記述不足が実装フェーズで発覚し、その場で直接改訂する**
   （`.specify/memory/constitution.md` セクション7「設計ルール」、2-1章）

- `CLAUDE.md` の命名規則・スコープ外機能は、`/speckit.plan` 実行前に埋めることが
  理論上は可能だったが、実際には実装（Structure Decision）が先に決まってから
  転記する形になった。
- `docs/tech-stack-template.md` のデザイントークン・E2Eツールは、そもそも
  実装してみないと決められない性質の項目だった。
- 憲法セクション7は「一度確定したら基本的に触らない」はずの箇所だが、
  抽象的すぎる記述だったために002の設計書作成中に手戻りが発生し、
  その場で必須セクションのチェックリストへ改訂された。

**論点**: ひな形として、こうした「実装後にしか確定しない記入欄」を
テンプレートにどう位置づけるか。
- (a) 現状通りプレースホルダーとして残し、各プロジェクトで実装後に手動で埋める運用を続ける
- (b) `/speckit.implement` 完了後に、実装内容からこれらの欄を自動反映する
  チェックリスト／コマンドをひな形側に用意する
- (c) 「実装確定後に記入する欄」であることをテンプレートのコメントとして
  明示し、記入漏れをレビューで検知しやすくする
