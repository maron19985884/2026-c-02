# Feature Specification: 注文完了画面

**Feature Branch**: `008-order-complete-page`
**Created**: 2026-09-09
**Status**: Draft
**Input**: User description: "注文完了画面（REQ-016〜018）：注文確定後に完了メッセージ・注文番号・商品一覧へ戻るリンクを表示する画面"

## Clarifications

### Session 2026-09-09

- Q: 注文完了画面をブラウザで再読み込み（リロード）した場合、同じ注文番号を再表示できるようにしますか？ → A: 再表示できるようにする（注文番号をURLに含め、バックエンドから注文情報を再取得して表示する）
- Q: カートの内容をクリアするタイミングはいつにしますか？ → A: 注文確定APIが成功した直後（フロントエンドが応答を受けてカート＝localStorageをクリアする）
- Q: 注文完了画面表示のための注文情報取得（GET /api/orders/:id 相当）が失敗した場合（該当注文が存在しない・通信エラー等）、どう振る舞いますか？ → A: 商品一覧画面へ自動的に差し戻す

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 注文完了メッセージを確認する (Priority: P1)

購入希望者として、注文フォーム画面で「注文する」を押した後、注文が正しく受け付けられたことを画面上のメッセージで確認できるようにしたい。これにより、購入手続きが最後まで完了したことを安心して確認できる。

**Why this priority**: 完了メッセージがなければ、購入希望者は注文が実際に成立したのか判断できず、購買フロー全体の信頼性が損なわれる。要件定義書でも REQ-016 は優先度「高」。

**Independent Test**: 注文フォーム画面で必要事項を入力し「注文する」を押した後、注文完了画面に遷移して注文が受け付けられた旨のメッセージが表示されることを確認するだけで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 注文フォーム画面で氏名・住所・メールアドレスをすべて正しく入力し「注文する」を押した、**When** 注文確定処理が成功する、**Then** 注文完了画面に遷移し、注文が受け付けられたことを示す完了メッセージが表示される。
2. **Given** 注文完了画面が表示されている、**When** 購入希望者が画面を見る、**Then** 追加の操作をしなくても完了メッセージがその場で視認できる。

---

### User Story 2 - 注文番号を確認する (Priority: P1)

購入希望者として、確定した注文を後で参照・問い合わせできるよう、注文完了画面で注文番号を確認できるようにしたい。

**Why this priority**: 注文番号がなければ、確定した注文を一意に特定する手段がなく、問い合わせ等に対応できない。要件定義書でも REQ-017 は優先度「高」。

**Independent Test**: 注文確定後に表示される注文完了画面に、当該注文を一意に識別できる注文番号が表示されることを確認するだけで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 注文確定処理が成功し注文完了画面が表示されている、**When** 購入希望者が画面を見る、**Then** 当該注文に対応する注文番号が画面上に表示される。
2. **Given** 複数回にわたって別々の注文を確定した、**When** それぞれの注文完了画面を確認する、**Then** 各注文完了画面には、それぞれの注文に対応する異なる注文番号が表示される。

---

### User Story 3 - 商品一覧へ戻る (Priority: P1)

購入希望者として、注文完了画面から商品一覧画面へ戻り、引き続き書籍を閲覧できるようにしたい。

**Why this priority**: 一覧へ戻る導線がなければ、購入希望者は注文完了後に次の行動（追加の閲覧・購入）に進めず、購買フローが行き止まりになる。要件定義書でも REQ-018 は優先度「高」。

**Independent Test**: 注文完了画面で「商品一覧へ戻る」リンクをクリックし、商品一覧画面へ遷移することを確認するだけで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 注文完了画面が表示されている、**When** 購入希望者が「商品一覧へ戻る」リンクをクリックする、**Then** 商品一覧画面へ遷移する。
2. **Given** 注文完了画面から商品一覧画面へ戻った、**When** 購入希望者がカートを確認する、**Then** 直前に確定した注文に含まれていた書籍はカートに残っておらず、カートは空の状態になっている。

---

### Edge Cases

- 購入希望者が、存在しない注文番号や不正な注文番号を指定するなど、有効な確定済み注文の情報を取得できない状態で注文完了画面に到達しようとした場合、注文完了画面は表示せず商品一覧画面へ差し戻す（[Clarifications Session 2026-09-09](#clarifications) 参照）。
- 注文情報の取得処理自体が通信エラー等で失敗した場合も、同様に商品一覧画面へ差し戻す（[Clarifications Session 2026-09-09](#clarifications) 参照）。
- 注文確定直後に注文完了画面を表示した後、購入希望者がブラウザの再読み込みを行った場合、注文番号をもとに注文情報を再取得し、同一の注文番号・完了メッセージを再表示する（[Clarifications Session 2026-09-09](#clarifications) 参照）。
- 注文完了画面到達後、ブラウザの「戻る」操作で注文フォーム画面に戻ろうとした場合でも、注文確定APIの成功直後にカートが既にクリアされているため、注文フォーム画面側の「カートが空の場合はカート画面へ差し戻す」という既定の挙動により、直前の注文が二重に確定されることはない。
- 注文完了画面到達後はカートが空になっているため、購入希望者がカート画面を直接開いた場合は、カート画面の空状態（0件）の表示に従う。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、注文確定処理が成功した場合に注文完了画面へ遷移させ、注文が受け付けられたことを示す完了メッセージを表示しなければならない（REQ-016）。
- **FR-002**: システムは、完了メッセージを購入希望者が追加の操作をしなくても画面上で視認できる形で表示しなければならない（REQ-016）。
- **FR-003**: システムは、確定した注文を一意に識別できる注文番号を注文完了画面に表示しなければならない（REQ-017）。
- **FR-004**: システムは、注文ごとに異なる注文番号を発行し、同一の注文番号が別の注文と重複しないようにしなければならない（REQ-017）。
- **FR-005**: システムは、注文完了画面に商品一覧画面へ戻るリンクを表示し、購入希望者がクリックすることで商品一覧画面へ遷移できなければならない（REQ-018）。
- **FR-006**: システムは、注文確定処理が成功した直後にカートの内容をクリアし、以降にカート・商品一覧画面を開いた際にカートが空の状態になっていなければならない（[Clarifications Session 2026-09-09](#clarifications) 参照）。
- **FR-007**: システムは、注文番号をもとに当該注文の情報を再取得できる形で注文完了画面を提供し、購入希望者がブラウザの再読み込みを行った場合も同一の注文番号・完了メッセージを再表示しなければならない（[Clarifications Session 2026-09-09](#clarifications) 参照）。
- **FR-008**: システムは、指定された注文番号に対応する有効な確定済み注文の情報を取得できない場合（存在しない注文番号・取得処理の失敗を含む）、注文完了画面を表示せず商品一覧画面へ差し戻さなければならない（[Clarifications Session 2026-09-09](#clarifications) 参照）。
- **FR-009**: 注文完了画面は未ログインの一般利用者が会員登録なしで閲覧できなければならない（要件定義書§2 対象範囲、ログイン・会員管理は対象外）。

### Key Entities

- **注文（Order、確定後）**: 注文フォーム画面での確定操作により成立した注文。注文番号・顧客情報・注文明細（対象書籍・数量・合計金額）を持つ。MySQLに永続化され、注文番号をキーに再取得できる。注文完了画面では、このうち少なくとも注文番号を表示する。
- **注文番号（OrderNumber）**: 確定した注文を一意に識別する識別子。注文確定時にシステムが発行し、注文完了画面に表示される。注文完了画面の表示・再表示（リロード時の再取得を含む）における注文の参照キーとしても用いられる（発行方式・具体的な形式は技術選定書 `tech-stack.md` に従い設計フェーズで定める）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 注文確定操作が成功した場合、100%の確率で注文完了画面に遷移し、完了メッセージが表示される。
- **SC-002**: 注文完了画面には、表示のたびに当該注文に対応する一意な注文番号が表示される（注文番号の表示漏れ・他注文との重複0件）。
- **SC-003**: 購入希望者は、注文完了画面から1回のクリック操作のみで商品一覧画面に戻れる。
- **SC-004**: 注文完了画面到達後にカート・商品一覧画面を開いた購入希望者のうち100%が、直前の注文に含まれていた書籍がカートに残っていない状態（カート0件）を確認できる。
- **SC-005**: 有効な確定済み注文の情報を取得できない状態（存在しない注文番号・取得失敗を含む）で注文完了画面へ到達しようとした場合、100%の確率で商品一覧画面へ差し戻され、完了メッセージ・注文番号が表示されることはない。
- **SC-006**: 注文完了画面を表示した直後に購入希望者がブラウザを再読み込みした場合、100%の確率で同一の注文番号と完了メッセージが再表示される。

## Assumptions

- 注文完了画面到達時にカートをクリアすることは、要件定義書に明記はないが、一般的な購買フローの前提として本仕様に含める（クリアのタイミングは[Clarifications Session 2026-09-09](#clarifications)で確定）。
- 注文完了画面が注文情報を注文番号ベースで再取得する具体的な実装（URLの形式、再取得APIのエンドポイント設計等）は技術選定書の構成に従い、設計フェーズで具体化する。
- 注文番号の発行方式・具体的な形式（桁数・文字種等）は技術選定書（`tech-stack.md`）§6に記載の方針に従う。本仕様では「一意に識別できる識別子であり、注文情報の再取得キーとしても利用できること」のみを規定する。
- 完了メッセージの具体的な文言・レイアウトの詳細は技術選定書に定めるCSS方針（CSS Modules）に従い、設計フェーズで具体化する。
- 検索・フィルター・レビュー・評価・ログイン・決済・在庫管理・管理画面などは要件定義書§2で対象外と明記されている（本画面にも適用）。
- 注文完了画面自体からの再注文（同一内容での再発注）機能は要件定義書に記載がないためスコープに含めない。購入希望者が再度注文する場合は、商品一覧画面へ戻ってから通常の購買フローをやり直す前提とする。
