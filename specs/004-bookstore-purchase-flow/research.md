## D-01: カート状態の保持方式

**Decision**: React の Context（`CartProvider`）でカート状態を保持し、変更のたびに `localStorage` へ同期する。初回マウント時に `localStorage` から復元する。

**Rationale**:
- FR-016 が「同一ブラウザにおいて永続的に保持し、タブやブラウザを閉じて再訪した場合にも復元する」ことを要求する。`localStorage` はブラウザを閉じても保持され、この要件に合致する。
- FR-016a が「端末・ブラウザを跨いで引き継がない」ことを要求する。`localStorage` はオリジン単位・ブラウザ単位で隔離されるため、この制約が自然に満たされる。
- `tech-stack.md` §6（却下した選択肢）に「カート状態は React の Context / useState ＋ `localStorage` で足りる規模のため（状態管理ライブラリを）導入しない」と明記されており、本決定はその記載の実装である。
- FR-032〜FR-034（全画面ヘッダーの件数表示を画面遷移なしで更新）を満たすには、カート状態がレイアウト直下で共有されている必要がある。`layout.tsx` で `CartProvider` を配置することで5画面すべてに行き渡る。

**Alternatives considered**:
- **サーバ側にカートを永続化（`carts` テーブル）**: 利用者を識別する手段がない（会員機能なし）ため、カートの持ち主を特定できない。識別用のトークンを別途発行することになり、要件にない仕組みが増える。却下。
- **`sessionStorage`**: タブを閉じると破棄されるため FR-016 を満たせない。却下。
- **Cookie**: 毎リクエストで送信され、サーバが使わないデータを往復させることになる。容量制限も厳しい。却下。

**Notes**:
- `localStorage` は読み書きが例外を投げうる（プライベートウィンドウ等）。読み書きを try/catch で包み、失敗時はメモリ上のカートとして動作を継続する（画面は壊さない・憲法§3）。
- 保存するのは `{ bookId, quantity }` のみとし、書名・価格は保存しない。価格は表示のたびに API から取得した最新値を使う（古い価格の表示を防ぐ）。確定価格の固定は注文時のスナップショットで行う（D-03 / FR-024）。

## D-02: 注文完了画面への注文情報の受け渡し

**Decision**: 注文確定の API 応答（注文番号）を `sessionStorage` に一時保存し、注文完了画面が**マウント時に読み出して即座に削除する**（一度きりの読み出し）。読み出せなかった場合は注文情報を表示せず、商品一覧への導線のみを表示する。

**Rationale**:
- FR-029b が「注文を特定できる情報（注文番号）を画面のアドレスに含めてはならない」ことを要求するため、`/order-complete/[orderNumber]` やクエリパラメータによる受け渡しは採用できない。
- FR-029a が「直前に確定した注文に対してのみ表示し、再読込・直接アクセス時は注文情報を表示しない」ことを要求する。読み出し時に削除することで、再読込すると自動的に「表示しない」状態へ落ちる。
- `sessionStorage` はタブ単位で隔離され、タブを閉じれば消える。ブックマークや履歴からの再訪で残らないため、FR-029a の意図に合う。
- 追加の依存を必要としない（`tech-stack.md` の範囲内）。

**Alternatives considered**:
- **URL に注文番号を含める（`/order-complete?order=XXXX`）**: FR-029b に正面から違反する。会員機能がなく閲覧者を識別できないため、番号を書き換えて他者の注文を閲覧できる穴になる。却下。
- **React の状態のみで受け渡す（`router.push` の state）**: Next.js App Router では画面遷移時の state 受け渡しに標準的な手段がなく、再読込で確実に失われる点は要件に合うものの、実装が不安定になる。`sessionStorage` の方が挙動が明示的。却下。
- **注文取得 API（`GET /api/orders/:orderNumber`）を設ける**: 認証なしで注文を引ける API になり、FR-029b の趣旨（他者の注文を閲覧させない）に反する。仕様の Assumptions でも注文履歴の閲覧を提供しないと明記済み。却下。

**Notes**: FR-029c に従い、注文完了画面には「この注文番号は再表示できません」旨を明示する。

## D-03: 注文番号の生成方式

**Decision**: ULID 形式（Base32 Crockford・26文字）の識別子を、Node.js 標準の `crypto.randomBytes` を用いて**バックエンドで自前実装**する。先頭48ビットはミリ秒精度のタイムスタンプ、残り80ビットは乱数とする。

**Rationale**:
- FR-023 が「注文を一意に特定できる注文番号」を、SC-005 が「複数回の注文で重複しない」ことを要求する。80ビットの乱数を含む ULID 形式は、本用途（ローカル・単一利用者）で衝突が実質的に起こらない。
- 時刻順に単調増加するため、`orders` テーブルで注文の並び順が自然になる。
- 利用者が画面から読み取って問い合わせに使える文字種（大文字英数字・紛らわしい文字を除外した Crockford Base32）である。
- `tech-stack.md` §6（却下した選択肢）に「注文番号（ULID 形式・Base32 26文字）は `crypto.randomBytes` を用いた十数行の自前実装で再現できるため、依存を追加しない」と明記されており、本決定はその記載の実装である。

**Alternatives considered**:
- **`ulid` npm パッケージ**: `tech-stack.md` §6 で明示的に却下済み（依存を増やさない方針）。却下。
- **DB の AUTO_INCREMENT を注文番号として使う**: 連番は他者の注文番号が容易に推測でき、桁数からおおよその注文数も推測できる。また `orders.id`（内部 ID）と注文番号が同一になり、外部に見せる識別子と内部 ID の分離ができない。却下。
- **UUID v4**: 一意性は十分だが36文字でハイフンを含み、利用者が読み上げ・書き写しするには冗長。時刻順にもならない。却下。

**Notes**: 注文番号は `orders.order_number` に `UNIQUE` 制約を置き、万一の重複時は INSERT が失敗して注文が成立しない（FR-026 の失敗時挙動に合流する）。

## D-04: 書籍の販売状態の表現

**Decision**: `books` テーブルに `is_available BOOLEAN NOT NULL DEFAULT TRUE` を設け、`TRUE` を販売中、`FALSE` を販売停止とする。一覧・詳細の取得クエリは常に `WHERE is_available = TRUE` を含める。

**Rationale**:
- FR-001a が「販売中か販売停止かを区別する状態を保持し、一覧・詳細のいずれにも販売中の書籍のみを表示する」ことを要求する（`/speckit.clarify` Q1 の決定）。
- 状態が2値しかない（販売中／販売停止）ため、BOOLEAN で十分。文字列の状態値（`'active'` / `'suspended'`）は値の揺れを招き、参照時に型で守れない。
- FR-001b により状態を変更する画面・操作は提供しないため、状態遷移の履歴を持つ必要がない。列1本で足りる。
- 在庫管理はスコープ外（§9）のため、在庫数との混同を避ける意味でも「販売可否」という単一の意味に限定する。

**Alternatives considered**:
- **`status VARCHAR` による状態値**: 将来の状態追加には強いが、管理画面がスコープ外で状態を増やす手段がない。`tech-stack.md` §8 の方針（依存・複雑さを増やさない）にも反する。却下。
- **販売停止の書籍を物理削除する**: FR-016b が「復元したカートに販売停止となった書籍または削除された書籍が含まれる場合、その旨を提示する」ことを要求しており、削除してしまうと「どの書籍が買えなくなったか」を利用者に伝えられない。また `order_items` からの参照も壊れる。却下。

**Notes**: 検証のため、`02_seed.sql` に `is_available = FALSE` の書籍を1冊以上含める（spec.md の Assumptions に記載済み）。

## D-05: 商品一覧の表示順

**Decision**: `ORDER BY id ASC` で固定する。

**Rationale**:
- FR-001d が「表示順を一定の規則で固定し、同じデータに対して再読込しても並びが変わらない」ことのみを要求しており、特定の並び順（新着順・価格順など）は要求していない。
- 検索・フィルター・並べ替えはスコープ外（§9）のため、利用者が並び順を変える手段はない。
- `id` は主キーで一意かつ不変のため、同じデータに対して必ず同じ並びになる。`ORDER BY` を省略した場合、MySQL は並び順を保証しないため FR-001d を満たせない。

**Alternatives considered**:
- **`ORDER BY created_at DESC`（新着順）**: 書店として自然だが、初期データが一括投入で `created_at` が同値になり、同値時の並びが不定になる。第2ソートキーが別途必要。要件が求めていない複雑さ。却下。
- **`ORDER BY title`（書名順）**: 日本語書名の照合順序（collation）に依存し、直感と異なる並びになりうる。却下。

## D-06: UI・CSS 方針

**Decision**: UI コンポーネントライブラリ・CSS フレームワークを導入せず、CSS Modules（`*.module.css`）と `frontend/src/app/globals.css` に定義する共有 CSS 変数（色・間隔・フォント）でスタイルを統一する。

**Rationale**:
- 憲法§3 は「UI はプロジェクトの技術選定書で定義した CSS フレームワーク・デザインシステムに準拠する。**未定義の場合はブラウザデフォルトスタイルを基準とし、プロジェクト内で統一する**」と定める。`tech-stack.md` は UI フレームワークを指定していないため、このフォールバックが適用される。
- 5画面・小規模であり、CSS Modules のスコープ分離だけでクラス名の衝突を防げる。Next.js が標準サポートしており追加依存が不要。
- 共有 CSS 変数を1箇所に置くことで、憲法§3 が求める「画面遷移・エラー表示・空状態の扱いを全画面で統一する」を、`ErrorNotice` / `EmptyState` の共通コンポーネント（FR-030）と合わせて担保できる。

**Alternatives considered**:
- **Tailwind CSS**: ユーティリティクラスで高速に組めるが、`tech-stack.md` に記載がなく、AI が技術を選び直すことになり憲法§5 に抵触する。却下。
- **MUI 等の UI コンポーネントライブラリ**: 同上に加え、5画面に対して依存が過大。却下。

> `tech-stack.md` §2「UI スタイル」欄および §6「却下した選択肢」から参照される決定。

## D-07: テストフレームワーク

**Decision**: フロント・バックともに Jest 29.x を使用する。バックエンドは `ts-jest` ＋ `supertest`、フロントエンドは `next/jest` ＋ `@testing-library/react` ＋ `jest-environment-jsdom` を用いる。`coverageThreshold` でカバレッジ80%を強制する。

**Rationale**:
- 憲法§2 が「主要なビジネスロジックには単体テストを必須」とし、カバレッジ目標を技術選定書で定義する（未定義なら80%）と定める。`tech-stack.md` §3 が80%を明記している。
- Next.js は `next/jest` による Jest 設定を公式にサポートしており、App Router 構成でも設定が最小で済む。
- Express の API 結合テストは `supertest` が事実上の標準で、実績が厚い。
- 単体テストの対象は SC-008 が挙げる3つ（合計金額の算出・入力バリデーション・注文番号の発行）に、注文スナップショット化を加えた4領域。いずれも純関数として切り出せる設計（`backend/src/domain/` / `frontend/src/lib/`）にすることで、DB やブラウザに依存せずテストできる。

**Alternatives considered**:
- **Vitest**: 設定が軽く高速だが、`tech-stack.md` §6 で明示的に却下済み（Next.js 公式サポートと Supertest の実績を優先）。却下。
- **テストなし／手動確認のみ**: 憲法§2 が「テストのない実装はレビューで差し戻す」と定めており、選択肢にならない。却下。

> `tech-stack.md` §2「テスト」欄および §6「却下した選択肢」から参照される決定。

## D-08: 注文確定の重複防止

**Decision**: 二段構えとする。
1. **フロント**: 「注文する」押下後、API 応答が返るまでボタンを `disabled` にする。
2. **バックエンド**: `orders.order_number` の `UNIQUE` 制約と、注文作成を単一トランザクション（`orders` INSERT → `order_items` INSERT → COMMIT）で処理することにより、途中失敗時に部分的な注文が残らないようにする。

**Rationale**:
- FR-025 が「同一の注文確定操作が重複して受け付けられないようにする」ことを要求する。
- 利用者の二重クリックはフロント側の無効化でほぼ防げる。これが第一の防御線。
- トランザクションにより、`order_items` の INSERT に失敗した場合に注文ヘッダだけが残ることを防ぐ。これは FR-026（失敗時は注文完了画面へ遷移せず、失敗を提示する）および FR-022b（失敗時はカートを空にしない）と整合する。
- requirements.md §4 の可用性要件がローカル・単一利用者を前提としており、複数利用者による同時注文の競合制御は不要（spec.md Assumptions に明記済み）。

**Alternatives considered**:
- **冪等キー（Idempotency-Key ヘッダ）と処理済みキーの永続化**: 通信断による再送まで防げるが、キーを保存するテーブルと有効期限管理が増える。単一利用者・ローカル前提の本要件に対して過剰。却下。
- **フロントのボタン無効化のみ**: 通信が遅い状況での連打は防げるが、サーバ側に一切の防御がなくなる。トランザクションは整合性のためにいずれ必要なので、併用する。単独採用は却下。

## D-09: フロントエンドのソースルート

**Decision**: `frontend/src/app/` を App Router のルートとする（`frontend/app/` ではない）。共有 CSS は `frontend/src/app/globals.css` に置く。

**Rationale**:
- `origin/main` の雛形が `frontend/src/app/layout.tsx` `frontend/src/app/page.tsx` の構成であり、`frontend/tsconfig.json` のパスエイリアスも `"@/*": ["./src/*"]` と `src/` を指している。雛形に合わせる方が変更が少なく、設定の齟齬も生じない。
- `tech-stack.md` §3 には `frontend/app/globals.css` という記載があるが、これは同文書が `src/` の有無まで確定させる意図で書かれたものではなく（同文書 §7 は「ファイル名（Next.js ルート）は Next.js の規約に従う」とのみ定める）、実在の雛形構成を優先するのが妥当と判断した。

**Alternatives considered**:
- **`frontend/app/` へ移す**: `tech-stack.md` の記載と字面が一致するが、雛形の既存ファイルとパスエイリアスを作り直すことになり、`tech-stack.md` §2 の「main ブランチの `frontend/package.json` で採用済み」という前提から離れる。却下。

> **要確認**: `tech-stack.md` §3 の `frontend/app/globals.css` という記載を `frontend/src/app/globals.css` に改めるかは、担当者（人間）の判断事項（憲法§5）。実装上の影響はパス表記のみ。

## D-10: 金額の型

**Decision**: 金額はすべて**整数の日本円**として扱う。DB は `INT UNSIGNED`、TypeScript は `number`、API の JSON も数値型で受け渡す。

**Rationale**:
- spec.md の Assumptions が「価格は日本円の単一通貨で、税込価格をそのまま表示・合計する。税額の内訳表示・税計算・割引・送料は行わない」と定める。日本円に小数の概念が実務上不要である。
- 小計・合計は「単価 × 数量」の整数演算のみで求まり（FR-010, FR-013）、浮動小数点の丸め誤差が入る余地がない。SC-003 が「表示値が単価×数量の総和と一致する（不一致0件）」を求めており、整数演算であれば厳密に満たせる。
- `DECIMAL` は誤差こそ避けられるが、`mysql2` が文字列として返すため、アプリ側で数値変換の処理が増える。

**Alternatives considered**:
- **`DECIMAL(10,2)`**: 多通貨・小数通貨に備えられるが、要件が日本円単一で税計算もない。`mysql2` の戻り値が文字列になり変換処理が増える。却下。
- **浮動小数点（`FLOAT` / `DOUBLE`）**: 金額計算に用いると丸め誤差が生じ、SC-003 を満たせなくなる。却下。

## D-11: API のエラー応答形式

**Decision**: エラー応答の本文を `{ "error": { "code": string, "message": string, "details"?: object } }` に統一する。HTTP ステータスは 400（入力不正）・404（不存在／販売停止）・409（カート内書籍が確定できない）・500（サーバエラー）を用いる。

**Rationale**:
- 憲法§3 が「エラー表示を全画面で統一する」ことを求め、FR-030 が同趣旨を要件化している。フロントの共通コンポーネント `ErrorNotice`（FR-030）が単一の形を前提にできれば、画面ごとのエラー処理の分岐がなくなる。
- FR-018 / FR-019 が「どの項目が未入力か」「形式が不正である旨」を利用者に示すことを要求するため、項目単位の情報を運ぶ入れ物（`details`）が必要。
- FR-016b が「販売停止・削除された書籍が含まれる場合、その旨を提示する」ことを要求するため、どの書籍が確定できなかったかを `details` で返す必要がある（409）。

**Alternatives considered**:
- **HTTP ステータスのみで表現し本文を返さない**: どの項目・どの書籍が問題かを伝えられず、FR-018 / FR-019 / FR-016b を満たせない。却下。
- **エラーごとに異なる本文構造**: フロント側の分岐が増え、憲法§3 の統一要件に反する。却下。

**Notes**: バリデーションはフロント（FR-018〜FR-020・即時のエラー表示）とバックエンド（`POST /api/orders` の最終防衛）の双方で行う。判定規則を一致させるため、両者のバリデーション関数は同じ規則を実装し、それぞれ単体テストを持つ（SC-008）。
