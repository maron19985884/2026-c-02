# Research: 注文フォーム・注文完了画面

`docs/tech-stack-template.md`で技術は確定済みのため、`[NEEDS CLARIFICATION]`項目は残っていない（注文永続化の方針自体はユーザーに確認済み、spec.md参照）。以下は実装方式に関する補足決定事項。

## 1. 注文番号の採番方式

**Decision**: 別テーブル・別カラムを設けず、`orders.id`（`AUTO_INCREMENT`）をそのまま採番元とし、`ORD-` + 6桁ゼロ埋め（例: `ORD-000001`）にフォーマットしてAPIレスポンス・画面表示のみで使用する。

**Rationale**: `AUTO_INCREMENT`のPKは、MySQLが単一トランザクション内で重複なく払い出すことを保証しており、一意性の要件（`requirements.md`用語定義）を満たす。フォーマットは表示専用の変換であり、`INSERT`後に採番済みの`id`から追加のクエリなしで導出できる。

**Alternatives considered**: `order_number`列を別途持ち、`INSERT`後に`UPDATE`で採番する方式。採番ロジックが複雑になり、トランザクション内のクエリが1本増えるだけの割に得られる柔軟性（`id`と無関係な採番規則）は本機能では不要なため見送った。

## 2. 注文商品の価格・書名のスナップショット方法

**Decision**: リクエストでは`bookId`と`quantity`のみを受け取り、書名・単価はクライアントの入力を信用せず、バックエンドが`books`テーブルから最新の値を取得して`order_items`に書き込む。

**Rationale**: 合計金額はサーバー側で再計算した値を正とすることで、クライアント側の改ざん・表示バグによって実際と異なる金額が記録されるリスクを避けられる（CLAUDE.md「安全なコードを書く」姿勢に合致）。また、書名・単価を注文確定時点のスナップショットとして保存することで、後で書籍情報が変わっても過去の注文内容は変化しない（spec.md Key Entities）。

**Alternatives considered**: フロントエンドが計算した小計・合計をそのままAPIに送信し、バックエンドはそのまま保存する方式。実装は単純だが、クライアント側の値を無条件に信用することになるため見送った。

## 3. 注文時点で対象書籍が販売対象外・存在しない場合の扱い

**Decision**: `POST /api/orders`は、リクエストに含まれる`bookId`のいずれかが存在しないか`is_for_sale = 0`の場合、注文全体を作成せず`400`を返す。

**Rationale**: カート画面（003）は販売対象外の書籍を注文対象から除外して表示するが、カート画面を開いてから注文フォームで確定するまでの間に他の要因で販売対象外になる可能性はゼロではない。全件が有効であることをサーバー側で保証してから永続化することで、注文明細に矛盾した状態（存在しない書籍を参照する注文）が残ることを防ぐ。

**Alternatives considered**: 無効な項目のみ除外して注文を作成する方式。利用者が注文フォームで確認した内容と、実際に保存される内容が一致しなくなるため見送った。

## 4. 注文の永続化に伴うトランザクション制御

**Decision**: `orders`への1件の`INSERT`と`order_items`への複数件の`INSERT`を、`mysql2`の単一コネクション上のトランザクション（`beginTransaction` / `commit` / `rollback`）でまとめて実行する。

**Rationale**: 注文ヘッダーと注文明細は必ず対で存在すべきであり、片方だけが保存された不整合な状態を避ける必要がある。

**Alternatives considered**: `pool.query()`を2回に分けて個別に実行する方式。2回目が失敗した場合に1回目の`orders`行だけが残ってしまうため見送った。

## 5. メールアドレスのバリデーション方式

**Decision**: `local@domain`の基本構造（`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`相当）を検証する正規表現を、フロントエンド（即時フィードバック用）とバックエンド（信頼境界での防御、CLAUDE.md参照）の両方に実装する。

**Rationale**: フロントエンドのみの検証では、API直叩き等でバリデーションを回避できてしまう。要件（spec.md Assumptions）が「実在確認は行わない」と明記しているため、形式チェックのみに留める簡易な正規表現で十分と判断した。

**Alternatives considered**: 外部のメール検証ライブラリの導入。本機能の要件（形式チェックのみ）に対して過剰であり、新規依存を増やすため見送った。

## 6. 注文確定後のカートのクリア方法

**Decision**: `POST /api/orders`が成功レスポンス（201）を返した後、フロントエンドが`cartStore.clear()`（新規追加）を呼び出してから注文完了画面へ遷移する。

**Rationale**: 注文が確定した書籍が引き続きカートに残っていると、利用者が誤って同じ内容を再度注文しかねない。API呼び出しの成功を確認してからクリアすることで、通信失敗時にカート内容を失わずに再試行できる。

**Alternatives considered**: 注文フォーム画面に入った時点でカートをクリアする方式。エラーで注文が失敗した場合にカートの内容を失ってしまうため見送った。
