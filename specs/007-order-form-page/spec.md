# Feature Specification: 注文フォーム画面

**Feature Branch**: `007-order-form-page`
**Created**: 2026-09-09
**Status**: Draft
**Input**: User description: "注文フォーム画面（REQ-012〜015）: カートから遷移し、氏名・住所・メールアドレスの必須入力とバリデーション、注文内容（カート）の同画面確認、「注文する」ボタンによる注文確定と注文完了画面への遷移を提供する"

## Clarifications

### Session 2026-09-09

- Q: カートが空（0件）の状態で購入希望者がURL直接アクセス等で注文フォーム画面に到達した場合、どう振る舞いますか？ → A: カート画面へ自動的に差し戻す（注文フォーム画面は「カートに1件以上ある」前提のみを扱う）
- Q: 氏名の入力欄は1つにまとめますか、姓・名で分けますか？ → A: 1つの入力欄にまとめる（要件定義書の記載に忠実）
- Q: 住所の入力欄は自由記述1行にしますか、郵便番号・都道府県などに分割しますか？ → A: 自由記述の1つの入力欄にする（要件定義書の記載に忠実）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 顧客情報を入力する (Priority: P1)

購入希望者として、注文フォーム画面で氏名・住所・メールアドレスを入力できるようにしたい。これにより、注文を届けるための最低限の情報をシステムに伝えられる。

**Why this priority**: 顧客情報が入力できなければ、バリデーション・注文確定を含む後続のすべての操作が成立しない。要件定義書でも REQ-012 は優先度「高」。

**Independent Test**: カート画面から注文フォーム画面へ遷移し、氏名・住所・メールアドレスの3項目の入力欄が表示され、それぞれに値を入力できることを確認するだけで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** カートに1件以上の書籍が入った状態で注文フォーム画面を開く、**When** 購入希望者が画面を見る、**Then** 氏名・住所・メールアドレスの入力欄がそれぞれ表示される。
2. **Given** 注文フォーム画面が表示されている、**When** 購入希望者が氏名・住所・メールアドレスのそれぞれに値を入力する、**Then** 入力した内容が各欄に反映される。
3. **Given** カートが空（0件）の状態、**When** 購入希望者がURL直接アクセス等で注文フォーム画面に到達しようとする、**Then** カート画面へ自動的に差し戻され、注文フォーム画面は表示されない（[Clarifications Session 2026-09-09](#clarifications) 参照）。

---

### User Story 2 - 入力内容のバリデーションを確認する (Priority: P1)

購入希望者として、氏名・住所・メールアドレスの入力に不備がある場合、注文を確定する前にエラーメッセージで知らせてほしい。これにより、誤った・不完全な情報のまま注文が進んでしまうことを防げる。

**Why this priority**: バリデーションがないと、届け先不明・連絡不能な注文が確定してしまい、購買フロー全体の信頼性を損なう。要件定義書でも REQ-013 は優先度「高」。

**Independent Test**: 氏名・住所・メールアドレスのいずれかを未入力のまま、またはメールアドレスを不正な形式で入力した状態で「注文する」を押し、エラーメッセージが表示され注文が確定しないことを確認するだけで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 氏名・住所・メールアドレスのいずれか1項目以上が未入力、**When** 購入希望者が「注文する」ボタンを押す、**Then** 未入力の項目についてエラーメッセージが表示され、注文は確定しない。
2. **Given** メールアドレス欄に「@」を含まないなど形式が不正な値が入力されている、**When** 購入希望者が「注文する」ボタンを押す、**Then** メールアドレスの形式が不正である旨のエラーメッセージが表示され、注文は確定しない。
3. **Given** 氏名・住所・メールアドレスの3項目すべてが入力され、メールアドレスの形式も正しい、**When** 購入希望者が「注文する」ボタンを押す、**Then** バリデーションエラーは表示されず、注文確定処理に進む。
4. **Given** エラーメッセージが表示されている状態、**When** 購入希望者が該当項目を修正して再度「注文する」ボタンを押す、**Then** 修正済みの項目についてはエラーメッセージが表示されなくなる。

---

### User Story 3 - 注文内容を同一画面で確認する (Priority: P1)

購入希望者として、顧客情報を入力する注文フォーム画面と同じ画面で、注文しようとしている書籍と合計金額を確認できるようにしたい。これにより、別画面を行き来せずに注文内容の最終確認ができる。

**Why this priority**: 注文内容を確認できないまま情報入力・確定に進んでしまうと、意図しない書籍・数量での注文につながる。要件定義書でも REQ-014 は優先度「高」。

**Independent Test**: カートに書籍が複数件入った状態で注文フォーム画面を開き、顧客情報の入力欄と同じ画面内に注文商品（カート内容）と合計金額が表示されることを確認するだけで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** カートに書籍が複数件入っている、**When** 購入希望者が注文フォーム画面を開く、**Then** 顧客情報の入力欄と同じ画面内に、カートに入っている各書籍と合計金額が表示される。
2. **Given** 注文フォーム画面が表示されている、**When** 購入希望者が顧客情報を入力する、**Then** 表示されている注文商品・合計金額は画面遷移なくそのまま確認できる状態を保つ。

---

### User Story 4 - 注文を確定する (Priority: P1)

購入希望者として、入力内容に問題がなければ「注文する」ボタン1つで注文を確定し、注文完了画面へ進めるようにしたい。これにより、購買フローを最後まで完結できる。

**Why this priority**: 注文確定手段がなければ、購買フロー全体が完結しない。要件定義書でも REQ-015 は優先度「高」。

**Independent Test**: 氏名・住所・メールアドレスをすべて正しく入力した状態で「注文する」ボタンを押し、注文完了画面へ遷移することを確認するだけで独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 氏名・住所・メールアドレスの3項目すべてが正しく入力されている、**When** 購入希望者が「注文する」ボタンを押す、**Then** 注文が確定し、注文完了画面へ遷移する。
2. **Given** 注文確定処理が行われている、**When** 購入希望者が操作を待つ、**Then** 「注文する」ボタン1回の押下のみで注文確定から画面遷移までが完了し、追加の確認操作は発生しない。

---

### Edge Cases

- カートが空（0件）の状態で購入希望者がURL直接アクセス等で注文フォーム画面に到達した場合、カート画面へ自動的に差し戻す（[Clarifications Session 2026-09-09](#clarifications) 参照）。注文フォーム画面は「カートに1件以上ある」前提のみを扱う。
- 氏名の入力欄は1つにまとめる（姓・名の分割は行わない。[Clarifications Session 2026-09-09](#clarifications) 参照）。
- 住所の入力欄は自由記述の1つの欄とする（郵便番号等への分割は行わない。[Clarifications Session 2026-09-09](#clarifications) 参照）。
- 「注文する」ボタンを連続で複数回押した場合、二重に注文が確定しないようにする（多重送信の防止は設計フェーズで具体化する前提とする）。
- 通信エラー等により注文確定処理自体が失敗した場合は、エラーメッセージを表示し注文フォーム画面にとどまり、入力済みの内容は保持する（入力内容の未入力・形式不正によるバリデーションエラーと同様、注文は完了画面へ進めない）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、注文フォーム画面に氏名・住所・メールアドレスの入力欄を表示し、購入希望者が値を入力できなければならない（REQ-012）。
- **FR-002**: システムは、氏名・住所・メールアドレスの3項目すべてを必須項目として扱わなければならない（REQ-012）。
- **FR-003**: システムは、「注文する」ボタンが押された時点で氏名・住所・メールアドレスのいずれかが未入力の場合、該当項目についてエラーメッセージを表示し、注文を確定させてはならない（REQ-013）。
- **FR-004**: システムは、「注文する」ボタンが押された時点でメールアドレスの形式が不正な場合、その旨のエラーメッセージを表示し、注文を確定させてはならない（REQ-013）。
- **FR-005**: システムは、エラーメッセージを、どの項目に不備があるかが購入希望者に判別できる形で表示しなければならない（REQ-013）。
- **FR-006**: システムは、注文フォーム画面と同一画面内に、カートに入っている注文対象の書籍（書名・数量等を含む）と合計金額を表示しなければならない（REQ-014）。
- **FR-007**: システムは、顧客情報の入力中も、表示されている注文商品・合計金額の確認のために別画面へ遷移する必要がないようにしなければならない（REQ-014）。
- **FR-008**: システムは、氏名・住所・メールアドレスの3項目すべてに不備がない場合、「注文する」ボタンの押下により注文確定処理を実行し、成功時は注文完了画面へ遷移させなければならない（REQ-015）。
- **FR-009**: システムは、注文確定を単一の「注文する」ボタン操作で完結させなければならない（確認画面等の追加ステップを挟まない）（REQ-015）。
- **FR-010**: システムは、注文確定処理が失敗した場合、エラーメッセージを表示して注文フォーム画面にとどまり、入力済みの顧客情報を保持しなければならない（Edge Cases 参照）。
- **FR-011**: 注文フォーム画面は未ログインの一般利用者が会員登録なしで閲覧・操作できなければならない（要件定義書§2 対象範囲、ログイン・会員管理は対象外）。
- **FR-012**: システムは、カートが空（0件）の状態で購入希望者が注文フォーム画面に到達した場合、カート画面へ自動的に差し戻さなければならない（[Clarifications Session 2026-09-09](#clarifications) 参照）。
- **FR-013**: システムは、氏名の入力欄を1つにまとめて提供し、姓・名を分割した入力欄は設けてはならない（[Clarifications Session 2026-09-09](#clarifications) 参照）。
- **FR-014**: システムは、住所の入力欄を自由記述の1つの欄として提供し、郵便番号・都道府県などに分割した入力欄は設けてはならない（[Clarifications Session 2026-09-09](#clarifications) 参照）。

### Key Entities

- **顧客情報（CustomerInfo）**: 注文確定に必要な入力情報。氏名・住所・メールアドレスの3項目からなり、いずれも必須。メールアドレスは形式チェックの対象となる。
- **注文（Order、確定前）**: 顧客情報とカートの内容（対象書籍・数量・合計金額）を組み合わせたもの。「注文する」ボタンの押下により確定され、成功時に注文完了画面へ引き継がれる（注文番号の発行等、確定後の詳細は注文完了画面の仕様範囲）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 購入希望者は、注文フォーム画面を開いた直後に、追加の操作なしで氏名・住所・メールアドレスの入力欄と、注文対象の書籍・合計金額を視認できる。
- **SC-002**: 氏名・住所・メールアドレスのいずれかが未入力のまま「注文する」を押した場合、100%の確率でエラーメッセージが表示され、注文は確定しない。
- **SC-003**: メールアドレスが不正な形式のまま「注文する」を押した場合、100%の確率でエラーメッセージが表示され、注文は確定しない。
- **SC-004**: 購入希望者は、注文フォーム画面から離れることなく、注文対象の書籍と合計金額を確認できる。
- **SC-005**: 氏名・住所・メールアドレスの3項目すべてに不備がない状態で「注文する」を押してから注文完了画面が表示されるまで、追加の確認画面や操作は発生しない（1回の操作で完了する）。
- **SC-006**: カートが空（0件）の状態で注文フォーム画面にアクセスしようとした場合、100%の確率でカート画面へ差し戻され、顧客情報の入力欄が表示されることはない。

## Assumptions

- メールアドレスの形式チェックは、一般的な「ローカル部@ドメイン部」の形式を満たすかどうかを基準とする一般的なメール形式バリデーションとし、具体的な正規表現・実装方式は設計フェーズ（`/speckit.plan`）で定める。
- バリデーションは「注文する」ボタン押下時にまとめて実施する方式を基本とし、入力中のリアルタイムバリデーション（フィールドからフォーカスが外れた時点でのチェック等）の要否・詳細は設計フェーズで具体化する。
- 「注文する」ボタンの多重クリック防止（連打による二重送信の抑止）や、注文確定処理中のローディング表示の具体的な見た目は本仕様では規定せず、設計フェーズで憲法§3のUX一貫性方針に沿って具体化する。
- 顧客情報の永続化方式・データベーススキーマは技術選定書（`tech-stack.md`）の構成に従う。本仕様では画面の入力・表示・遷移の要件のみを規定する。
- 注文番号の発行方式は注文完了画面（REQ-016〜018）の仕様範囲であり、本画面では注文確定に伴い注文完了画面へ遷移することのみを規定する。
- 送料などの金額計算・表示ルールは要件定義書§2で対象外と明記されている（本画面で表示する合計金額はカート画面の合計金額と一致する）。
- 検索・フィルター・レビュー・評価・ログイン・決済などは要件定義書§2で対象外と明記されている（本画面にも適用）。
- 注文フォーム画面のレイアウト・デザインの詳細（項目の並び順、レスポンシブ対応の具体仕様等）は技術選定書に定めるCSS方針（CSS Modules）に従い、設計フェーズで具体化する。
